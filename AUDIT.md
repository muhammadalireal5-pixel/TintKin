## 2026-10-25, scalability audit (user-requested: "can this handle 10k concurrent users?", ignoring Vercel/Atlas free-tier limits)

**Findings only, no code changed.** Read-only review of `mongoose.js`, `auth.js`, `proxy.js`, `actions.js` (scan, dashboard, leaderboard, percentile), `plan.js`, `quota.js`, `rate-limit.js`, `youcam.js`, `qwen.js`, the reminders cron, `AppShell`/`Companion`. **Nothing was load-tested or run**, so every "will fail at N" below is reasoning from the code, not a measurement. Planning figure: 10k concurrent users ≈ 200–500 req/s at peak, not 10k simultaneous requests.

**What is already sound:** JWT sessions (no session table), DB-backed atomic rate limiter, atomic quota reservation, cached Mongo connection with retry, indexes on the core `userId + date` paths, capped history queries, timeouts on every vendor call, no client network polling (the 14s interval in `Companion.jsx` is animation only).

### Likely to break first (fix before a real launch)

## 2026-10-14, third pass (user-reported: /leaderboard shows "Something unexpected happened" every time)

- **Leaderboard crash — fixed. Root cause confirmed directly in Next's own bundled RSC client runtime, not guessed.** `app/leaderboard/page.jsx` (a Server Component) calls the `"use server"` action `getLeaderboard()` unawaited and passes the resulting promise to `LeaderboardClient.jsx` as `initialDataPromise` — the same "stream a promise, consume it client-side" pattern the 2026-10-12 follow-up pass used for `/history` and flagged as "not verified call-site-by-call-site... worth a dedicated pass." This was that bug. Once a promise like this crosses the server→client boundary, the object the client actually receives is React's internal `ReactPromise` "chunk" (`node_modules/next/dist/compiled/react-server-dom-turbopack/cjs/react-server-dom-turbopack-client.browser.development.js:5053`), not a native `Promise`. Its `.then(resolve, reject)` exists — `await` and `use()` both work fine, which is why `CaptureClient.jsx`'s identical pattern (`precheckPromise.then(cb)`, never chained further) was unaffected — but the function **never returns anything**. `LeaderboardClient.jsx` and `HistoryClient.jsx` both did `thatPromise.then(...).catch(...)` (`HistoryClient` also chained `.finally(...)`), so `.then()` evaluated to `undefined` and the next link in the chain threw `TypeError: Cannot read properties of undefined (reading 'catch')` — on literally every page load, inside React's effect-commit phase, caught by `app/leaderboard/error.js`'s error boundary ("Something unexpected happened"). **Fix:** both effects now do `Promise.resolve(thatPromise).then(...).catch(...)` — `Promise.resolve` on a thenable adopts its resolution via a single `.then(resolve, reject)` call (which `ReactPromise` properly supports) and hands back a real, chainable native `Promise`. Checked every other `.then(` site in the app for the same shape; `CaptureClient.jsx`'s two streamed promises and `app/what-if/page.jsx` don't chain past the first `.then()`, so they were never at risk.
- **Google-avatar CSP block — fixed, found incidentally while reading the same console output.** `proxy.js`'s `img-src` CSP directive only allow-listed `res.cloudinary.com` and the YouCam S3 bucket; a Google OAuth account's `photoURL` (`lh3.googleusercontent.com`) was silently blocked by the browser everywhere it's rendered as an `<img>` (dashboard header, leaderboard rows, `LeaderboardCard`, `TrophyCase`, `ShareCard`). Added `https://lh3.googleusercontent.com` to `img-src`.
- **Re-verified:** `bun run test` 31/31, `bun run lint` clean on every file touched (pre-existing `<img>`/apostrophe warnings elsewhere untouched), `bun run build` compiles cleanly.

## 2026-10-13 pass (user-requested: review an external audit report, fix what verified as real)

An external security review (pasted in by the user) raised a batch of findings. Same convention as every other pass here: each claim was checked against source before anything was changed, not taken at face value either way.

**Confirmed and fixed:**
- **Client-IP trust — new finding, the real mechanism behind the report's rate-limit-DoS claim.** `auth.js`, `app/lib/admin-auth.js`, and `app/lib/auth-actions.js` all derived the rate-limit IP via `x-forwarded-for.split(",")[0]` — the *first* entry, which is whatever the client itself put there (each hop in a proxy chain *appends* its own observed address; it doesn't overwrite earlier ones). That let an attacker (a) collide with a victim's login/register/password-reset rate-limit key by sending `X-Forwarded-For: <victim's real IP>` plus the victim's email, locking the victim out, and (b) bypass the admin-login and register-IP-only caps entirely by sending a fresh fake IP on every request — a straight brute-force-throttle bypass, not just a victim-targeting trick. All three call sites also fell back to a literal `"unknown"` string when no IP header was present, collapsing every such request into one shared, fully attacker-predictable key. **Fix:** new `app/lib/request-ip.js` (`getClientIp`) trusts the *last* `x-forwarded-for` entry instead (what our own edge/single reverse-proxy hop actually observed, not client-settable), falls back to `x-real-ip`, and returns `null` — never a shared sentinel — when neither header is present. New `checkOriginAwareRateLimit` (`app/lib/rate-limit.js`) never folds a null IP into an email-keyed check; it instead applies one shared, email-independent floor (`NO_ORIGIN_FLOOR`, 10/hour) across all such traffic for that action, so a no-origin attacker degrades the fallback path for everyone (including their own next attempt) instead of getting a key that targets one victim. Applied to login (`auth.js`), registration's identity check and password-reset (`app/lib/auth-actions.js`), and admin login's IP extraction (`app/lib/admin-auth.js`). New tests: `tests/request-ip.test.mjs` (4/4 pass). **Assumes exactly one trusted hop in front of the app** (true for a single Vercel deployment, or one self-hosted reverse proxy) — re-check this if that topology ever changes; this is the same deployment-trust boundary L5 already flagged, now actually closed for the common case instead of left open.
- **Password-reset suppression attack — fixed.** `requestPasswordReset` (`app/lib/auth-actions.js`) rate-limited on `getCompositeKey("server-action", email)` — email alone, no IP at all (the comment claimed "server actions don't have direct IP context," which is incorrect — `registerUser`, two functions above in the same file, already reads `headers()` directly). Anyone who merely knew a victim's email could burn their 3/hour budget with zero credentials, and every request after that — including the real victim's — hit the "rate limited" branch, which silently returns `{success: true}` with no email sent (to avoid account-enumeration). The victim saw "check your email" and got nothing, with no error to act on. Now uses the same IP+email `checkOriginAwareRateLimit` as the other identity checks above.
- **Admin logout CSRF — fixed.** `POST /api/admin/logout` called `adminLogout()` (which stamps a global `revokedBefore`, invalidating every admin session) with no check that the caller held a valid admin session at all — any external site could force this via a cross-origin POST, logging out whoever was actually signed in as admin. Now calls `verifyAdminSession()` first and returns 401 without touching any state if there's no valid session.
- **Free-tier denial message — fixed.** `reserveSlot` (`app/lib/quota.js`) checked `daily_limit` before `monthly_limit` and returned on the first hit, so a free user who'd exhausted both got "come back tomorrow" — which wouldn't actually help, since the month was also spent. Monthly is now checked first, so the more restrictive/accurate reason wins when both are exhausted.
- **Age bug in the advice prompt — fixed.** `generatePersonalizedAdvice` (`app/lib/qwen.js`) used the same `currentYear - birthYear` bug already fixed everywhere else via `calculateAge()` (L9 and its two 2026-10-05 follow-ups) — this one call site was missed across all of those passes. Now uses `calculateAge()`.
- **Test resolver bug — fixed.** `tests/setup/resolve-hooks.mjs` appended `.js` to *any* bare specifier that failed to resolve and had no `.js`/`.mjs`/`.cjs` suffix — including real package names that contain a dot (`@sentry/nextjs` → `@sentry/nextjs.js`), turning a correctly-failing resolution into a differently-wrong one. The `.js` retry now only applies to `@/`-aliased or relative specifiers. **Not currently reproducing in this environment** — the full suite gives the same result before and after this specific fix (same 3 pre-existing, unrelated failures in `youcam.test.mjs`); the logic was still a real bug worth closing defensively, but whatever produced the originally-reported "fails to even load" symptom isn't present in this checkout right now.

**Checked against source and corrected, not taken at face value:**
- The report's first description of the rate-limit DoS (session-scoped victim lockout from any IP) doesn't hold *as described* — the composite key already includes IP, so a cross-IP attacker can't collide with a victim's key unless IP itself is spoofable. It is, which is the actual bug fixed above; the original framing was wrong about the mechanism, not about there being a real problem.
- **"Shared limiter budget for verification/resends"** — `resendVerificationEmail` and `requestPasswordReset` reuse the same action label and numeric config, but different `identifier` values (`email-verify:<uid>` vs. the email hash), and `checkRateLimit` keys on `(identifier, action, windowStart)` — so they're separate counters, not one shared budget. `resendVerificationEmail` also requires an authenticated session, so it isn't reachable by an anonymous attacker targeting an arbitrary victim the way `requestPasswordReset` was. Not changed.
- **Fail-open on DB outage** (`rate-limit.js`, any DB error during `checkRateLimit` returns `allowed: true`) — confirmed real, but it's a deliberate, commented, Sentry-reported tradeoff favoring availability over a hard lockout during an outage, not an oversight. Left as-is; noted here in case that tradeoff is ever revisited.

**Not in scope for this pass** (bigger, product/architecture calls, left for the user as usual): deferring Qwen advice generation out of the request path via the existing `adviceStatus: 'pending'` enum (sound idea, grounded in infra that already exists — not done here); the self-hosting IP-trust boundary if this app is ever deployed behind more than one proxy hop; everything else the external report raised that was already sitting in this file's Open list (free-tier-looks-broken, leaderboard "anonymous" copy, personal Gmail contact, M22 migration, CSP-static-page tradeoff, login-lockout-no-unlock-path).

Two independent, stackable causes were found and both addressed: (1) it returned `null` with zero explanation whenever there were no analyzed scans with a score to plot — replaced with a "not enough analyzed scans yet" message. (2) its chart container inherited height via `h-full`/`flex-1` through `DashboardSection`'s Framer Motion `height: 0 → "auto"` expand animation — a well-documented Recharts+animated-height interaction where `ResponsiveContainer`'s `ResizeObserver` can capture a transient 0px measurement and never recover, rendering nothing even with valid data. - **Scan consent + photo-storage choice — added.** A new one-time, non-dismissible modal (`ScanConsentModal.jsx`) appears the first time a user tries to scan (gated in `capture/page.jsx`'s `handleActionClick`, before the camera/gallery picker opens): a required "I agree to the Terms of Service and Privacy Policy" checkbox plus the existing store-vs-delete photo choice (previously a silent default buried in Settings, never actually asked). `User.termsAcceptedAt` (new field, doubles as a consent timestamp) is set once by the new `acceptScanConsent` action; `analyzeAndSaveSelfie` also rejects server-side if it's unset, so the gate can't be bypassed by calling the action directly. - **M19, actually completed.** The original finding named four functions; only `getLatestData` was fixed in the first pass. `getWeeklyHistory()` loaded the user's *entire* scan history, unprojected and non-lean, to compute a chart that only ever shows the most recent 12 weeks — now bounded to the last 100 days with a narrow field projection. `getPercentileRank()`'s peer lookup had no limit at all and, unlike the leaderboard, isn't narrowed by location — any user whose age bracket got large (no geography filter) could make this scan a big chunk of the whole user table; added `.select("_id").lean().limit(5000)`, since only `_id` was ever used from the result. `getSavedSimulations()` already had `.lean()` and simulations are inherently rate-limited to a handful a month, so it was left alone.
- **Signup age gate — fixed, found while answering the user's legal-compliance question.** `app/terms/page.jsx` §4 states users must be 18+, but `lib/validations/onboarding.js` only enforced 13+, using the same naive `currentYear - birthYear` subtraction already fixed elsewhere (L9) — meaning a 13-17 year-old could create an account and upload facial biometric data in direct contradiction of the stated Terms, and with real exposure under child-biometric-data rules (Illinois BIPA, GDPR Art. 8) that the 18+ line was presumably meant to sidestep entirely. ### Scalability, security, legal — findings, not fixes

Answering the user's direct questions required real investigation, not just an opinion; this section is why `AUDIT.md` now says what it says in the summary given back to them. Nothing below was changed without being listed as a fix above — these are the parts that need the user's own decision (legal review, a growth plan) rather than a one-sided code change:

- **Rate limiting is DB-backed (Mongo, atomic `findOneAndUpdate` upserts, TTL-indexed), not in-memory** — correctly built to work across multiple serverless instances, which an in-memory counter would not.
- **Mongo connection pooling is capped at `maxPoolSize: 10`** (`app/lib/mongoose.js`) per serverless instance; fine at the scales discussed (100–10,000 users) on any paid Atlas tier, but worth knowing it's a per-instance cap, not a global one — Vercel can spin up many concurrent instances under load, each opening its own pool.
- **Privacy policy is out of date relative to the actual codebase**, independent of today's fixes: it names MongoDB Atlas, Cloudinary, PerfectCorp/YouCam and Alibaba Cloud/Qwen as processors but never mentions **Resend** (emails, including the new export/verification features) or **Sentry** (error monitoring) — both real processors of user data today. It also describes images as kept only "temporarily... during that session", which undersells how long a `photoPrivacy: store` user's single photo is actually kept (until their *next* scan, which could be weeks later).
- **Cross-border data transfer**: Alibaba Cloud (Qwen) is based in China, which has no EU adequacy decision — if any EU resident's data reaches it (the policy says only numerical scores, not images, but scores are still personal data), that needs a documented transfer safeguard (SCCs or equivalent) that isn't mentioned anywhere. This is a genuine GDPR Chapter V exposure point, not a style nitpick.
- **No lawful basis or retention period stated** for non-image data, which GDPR Art. 13 requires explicitly, and no CCPA-specific disclosures (categories collected/shared, opt-out mechanism framing) beyond "we don't sell images".
- None of the above were rewritten here — redrafting a privacy policy/terms of service is a legal-review task, not something to silently ship. Flagged for the user to take to counsel, with the concrete gaps listed above as a starting point.

## 1. The reported error: What-If simulation fails (`error_download_image`)

**Severity:** Critical (functional). The core feature failed for every user without a custom photo. **Status:** Fixed – tested.

**Symptom:** the UI showed "Simulation failed. Please try again later." The terminal showed `simulateSkin failed (skin-simulation task): Error: error_download_image`, which was only visible after adding logging; it had previously been swallowed silently.

**Root cause (confirmed):** a display-only signed URL was reused as the input for a transformation.

1. `getLatestData()` (`app/lib/actions.js`) replaces `latestSelfie.imageUrl` with a **signed** delivery URL: `…/image/upload/s--SIG--/<publicId>` (`signCloudinaryUrl`, `lib/utils/cloudinary-sign.js:46`).
2. `runWhatIfSim()` gets its source image from `getLatestData()`, so it receives that signed URL.
3. `simulateSkin()` (`app/lib/youcam.js:254`) crops it with `applyFaceCropToCloudinary` (`lib/utils/cloudinary.js:116`). That function split the URL on `/upload/` and inserted the crop **in front of the signature**: `…/upload/c_thumb,g_face,…/s--SIG--/<id>`. Cloudinary treats `s--SIG--` as part of the public ID, so the URL doesn't resolve and YouCam reports `error_download_image`.
4. `simulateSkin` only retried face-size/bounds errors. The download error therefore aborted on the first candidate URL, and the fallback URLs (another crop and the original) were never tried.
5. Its catch block also replaced the real error with a generic string and logged nothing.

Scans worked because the capture page passes the fresh, **unsigned** upload URL straight to `analyzeSkin`.

**Related damage from the same pattern (confirmed):**
- The "Without Routine" baseline image of every simulation was stored with the same broken URL.
- `signCloudinaryUrl` returned already-signed URLs unchanged, and dropped existing transformations when it re-signed. Saved simulations therefore showed a broken or uncropped baseline next to a cropped simulated image.
- `getCloudinaryPublicId` didn't strip `s--…--`, so deleting an image by its signed URL silently did nothing.

**Fix:**
- `applyFaceCropToCloudinary` removes the signature before adding a transformation. Selfies are public `upload` assets, so the unsigned crop can be delivered; this matches what `analyzeSkin` already relies on.
- `getCloudinaryPublicId` skips signature segments.
- `signCloudinaryUrl` always re-signs, keeping the URL's own transformations inside the signature. This also **repairs** legacy records stored in the broken shape at read time, with no data migration needed.
- `simulateSkin` and `analyzeSkin` treat download failures as retryable and fall back to the next candidate URL.
- Failures are logged with the YouCam error code only, never the raw response body (which can contain image URLs).
- `runWhatIfSim` logs its failure message to the server terminal.

**Verification:**
- `tests/cloudinary.test.mjs` and `tests/youcam.test.mjs` (11 tests) cover: crop-of-signed-URL, re-signing with crop, legacy URL repair, idempotence, and fallback on `error_download_image` with a mocked YouCam.
- Running the old `applyFaceCropToCloudinary` from HEAD against a signed URL reproduces exactly `…/upload/c_thumb,…/s--AbCd12_---/abc123`, so the regression test would fail on the old code.
- **Not yet verified end-to-end against live YouCam/Cloudinary.** See manual action M1.
